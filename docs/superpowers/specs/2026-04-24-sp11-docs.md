# SP-11 — Quickstart + Integration + Protocol Docs Design Spec

**Date:** 2026-04-24
**Status:** Design approved; plan pending.
**Scope:** Ship 9 reference-grade documentation files under `docs/quickstart/`, `docs/integrations/`, and `docs/protocol/`. Depth C (comprehensive reference, 400-800 lines each). Source material comes from SP-6 / SP-7 validation docs + SP-10 adapter examples + direct reading of `atd-types` and `atd-client` source. No new code or tests.
**Builds on:** `sp10-adapters` — 252 workspace tests, LLM adapters in Rust + Python LangChain. 

---

## 1. Motivation

The SP-9 public README (v0.1.0) tells an outsider what atd-mvp is and how to run the `hello_atd` demo. After the demo, there's nowhere to go. Real adoption — a developer wiring ATD into their LangChain agent, a team standing up the MCP bridge for Claude Desktop, an implementer building a third-party ATD server — requires reference material that doesn't yet exist.

Design.md §4 lists 10 such documents. SP-11 ships 9 of them (protocol/bindings.md folds into wire-format.md) at Depth C — full reference, not one-pagers. The bet: a comprehensive docs set invests hours now to avoid dozens of "how do I..." interactions per adopter later.

---

## 2. Scope

### 2.1 In scope

9 documentation files. Depth C: each is reference-grade (400-800 lines) with walk-throughs, complete field tables, common pitfalls, and troubleshooting where applicable.

**Quickstart (3 files):**
- `docs/quickstart/rust.md` — Rust SDK from `cargo add atd-client` through first call + adapter usage + error handling
- `docs/quickstart/python.md` — Python SDK through `pip install -e python/` (local dev) + first call + LangChain adapter + sync/async variants
- `docs/quickstart/typescript.md` — placeholder stub (~200 lines). Explains current state (not shipped), the planned API shape, points at the Rust quickstart as interim reference.

**Integrations (4 files):**
- `docs/integrations/langchain.md` — LangChain Python agent + ATD tools. Full AgentExecutor walk-through, StructuredTool internals, error surfaces, streaming/async considerations.
- `docs/integrations/hermes.md` — Hermes Agent with MCP bridge. `hermes mcp add` flow, provider selection, troubleshooting (based on real SP-7 experience).
- `docs/integrations/claude-code.md` — Claude Desktop, Claude Code, Cursor (three-way). Comparison of each client's MCP config format, example session.
- `docs/integrations/openclaw.md` — Stub (~200 lines). Current state (not natively integrated), interim workaround via MCP bridge, future skill-publication plan.

**Protocol (2 files):**
- `docs/protocol/wire-format.md` — The ATD wire protocol in full. Length-prefixed JSON framing, all message types (discover/describe/call/ping + extension), error propagation semantics. Absorbs the "bindings" doc's content as a section.
- `docs/protocol/error-codes.md` — `AtdError` reference. Every variant with trigger conditions, `is_retryable()` value, `suggest_fix()` output, recovery strategy.

### 2.2 Explicitly out of scope

- **New code or behavior** — docs only. No implementation changes, no new tests.
- **`docs/protocol/bindings.md` as a separate file** — merged into wire-format.md's "Server Bindings" section.
- **TypeScript SDK** — referenced as planned, not implemented. Quickstart is a placeholder.
- **Deep OpenClaw integration** — no ClawHub skill exists; doc is a placeholder explaining the gap.
- **Updating README to include all doc links** — small and in-scope (Task 3 step), not a separate SP.
- **Syncing docs on every code change going forward** — governance, not a doc SP.

### 2.3 Prerequisites

- `sp10-adapters` tag, 252 workspace tests green.
- All existing SP-6/SP-7 validation docs + SP-10 examples must exist (they're the primary source material).
- `crates/atd-types/src/error.rs` and `crates/atd-types/src/tool.rs` authoritative for protocol + error fields.

### 3.8 `docs/protocol/wire-format.md`

Target: 600-800 lines.

**Sections:**
1. **Overview** — length-prefixed JSON over Unix socket / stdio. No HTTP yet.
2. **Framing** — 4-byte big-endian u32 length prefix + UTF-8 JSON body. Max body size (10 MiB).
3. **Connection lifecycle** — connect → optional session.start → request/response round trips → disconnect
4. **Message types** — one subsection per type:
   - `ping` / `pong` — liveness check
   - `discover` — query + filter + limit → `[ToolSummary]`
   - `describe` — tool_id → `ToolDefinition`
   - `call` — tool_id + args + options → `ToolResult`
   - (future) `session.start` / `session.end`, `cancel` — noted as "planned, not in v0.1.0"
5. **Full type definitions** — pasted from atd-types Rust source, annotated with field semantics. ToolSummary, ToolDefinition, ToolResult, ToolSafety, ToolCapability, enums (SafetyLevel, ToolVisibility, TrustLevel, ToolTier, BindingProtocol).
6. **Server bindings** — how a tool gets implemented behind an ATD server. CLI binding (shell command), MCP binding (forwarding to MCP server), REST binding (HTTP proxy), AppFunction binding (Phase 2). Absorbs the content originally planned for `docs/protocol/bindings.md`.
7. **Error propagation** — link to error-codes.md for full taxonomy; show wire shape of `ToolResult::Error`.
8. **Versioning** — 0.x = breaking-allowed, 1.0 = protocol-stable promise. How to detect protocol version mismatches.
9. **Extension points** — the `_atd` MCP extension object, custom fields.
10. **Reference: MCP compatibility** — map of ATD request types to MCP operations, sanitization rules.

### 3.9 `docs/protocol/error-codes.md`

Target: 400-500 lines.

**Sections:**
1. **Overview** — two error layers: `AtdError` (client-side) and `ToolResult::Error` (server-reported). Their relationship.
2. **Full `AtdError` table** — each variant:
   - Definition (from atd-types)
   - Trigger conditions (what causes the server / network / protocol to produce this)
   - `is_retryable()` return value
   - `suggest_fix()` return value
   - Example client code showing recovery

   The 9 variants to cover: `ToolNotFound`, `InvalidArguments`, `CapabilityDenied`, `BindingUnavailable`, `ToolExecutionFailed`, `Timeout`, `ServerUnreachable`, `NotImplemented`, `ProtocolError`.
3. **Server-side error codes** — the `code` string in `ToolResult::Error`. Common values: `NOT_FOUND`, `INVALID_ARGS`, `NOT_AVAILABLE`, `TIMEOUT`, `TLS_FAILED`, `TOO_MANY_REDIRECTS`, `PRIVATE_ADDRESS_BLOCKED`, `IO`, `NOT_A_DIRECTORY`. For each: which tool(s) emit it, is the caller supposed to retry?
4. **Retry decision tree** — when `is_retryable: true`, what should the caller do? Exponential backoff? Jitter? Per-error strategies.
5. **Debugging errors** — enabling wire logs, correlating client error with server log, common gotchas.

## 5. Tone and conventions

- **Audience:** professional developers with 2-5 years of experience, Rust/Python fluent. Not CS undergrads, not managers.
- **Voice:** second-person ("you"), active, declarative. Minimal meta-commentary. English only (no zh-CN mix; project is English-dominant).
- **Code samples:** every code block runnable as-is; no pseudocode. Paths absolute where machine-specific, placeholder-tagged where user-specific (`/path/to/atd-mvp`).
- **Length targets:** stated in §3 per doc. Tests against them are soft (±20% OK); sections missing is a fail.
- **Cross-references:** explicit paths (`docs/quickstart/python.md`), not just "see quickstart". Hyperlinks in README.
- **Placeholders:** use `<YOUR_SOCKET_PATH>` / `<YOUR_API_KEY>` etc. with clear "replace this" framing; do NOT leave raw `<YOUR_USERNAME>` that could escape into published artifacts (SP-9 hand-off already showed why).

## 6. Risks and non-risks

### 6.1 Risks

**R1 — docs drift from code.** 9 docs of 400+ lines each will go stale as code evolves. Mitigation: future iterations should edit the docs as part of any PR that changes API shape. Not enforced in SP-11 — future governance problem.

**R2 — readers hit commands that don't work in their env.** Shell commands assume Linux + Rust toolchain; macOS/Windows users may see drift. Mitigation: each quickstart has an "Environment" note at top listing what's tested (Linux) and pointing at platform-specific call-outs where they exist.

**R3 — TypeScript quickstart feels like false advertising.** Shipping a quickstart for an SDK that doesn't exist is awkward. Mitigation: the doc leads with "NOT SHIPPED" in visible framing, explains the design, and redirects to Rust. An honest stub beats leaving the path 404'd.

**R4 — wire-format.md becomes out-of-sync with actual serde output.** Copy-pasted type definitions could drift. Mitigation: include "source: `crates/atd-types/src/summary.rs` at commit sp10-adapters" near the top of the type tables.

### 6.2 Non-risks

- **Length:** Depth C's 400-800 lines per file is well-supported by a Sonnet-level subagent in a single task. No token limit concern.
- **Accuracy:** primary sources (SP-6/SP-7 validation, atd-types source) are authoritative and recent. Content is restatement not invention.
- **Test breakage:** no code changes. `cargo test` + `pytest` unaffected.

## 7. Exit criteria

1. All 9 doc files exist at their spec'd paths
2. Each file's length within ±20% of its spec'd target
3. Each file's top-level section headings match the outline in §3
4. All shell/code blocks in each doc are copy-paste runnable in a Linux + Rust/Python env (manual spot-check, not automated)
5. Root `README.md` has a "Documentation" section linking all 9 docs
6. `grep -l '<YOUR_SOCKET_PATH>\|<YOUR_API_KEY>' docs/` finds the placeholders (so they're present and consistent)
7. `grep -rn '^# ' docs/quickstart/ docs/integrations/ docs/protocol/` lists 9 h1 headings (one per file)
8. `cargo test --workspace --all-targets` unaffected (252 tests, 0 failures)
9. Tag `sp11-docs` at the final commit

---

## 8. What SP-11 does NOT accomplish

- External adoption — docs being good doesn't drive adopters; distribution (SP-9 actual publish) + announcement do that.
- Multi-platform support — docs assume Linux for shell snippets; macOS/Windows gaps stand.
- Protocol stabilization — wire-format.md describes the current shape, but doesn't freeze it (0.x contract still in force).
- TypeScript SDK — remains unshipped.
- OpenClaw native integration — remains unimplemented.
