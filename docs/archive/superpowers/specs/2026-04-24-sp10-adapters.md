# SP-10 — LLM Adapters Design Spec

**Date:** 2026-04-24
**Status:** Design approved; plan pending.
**Scope:** Ship LLM-provider adapters in the Rust client (OpenAI / Anthropic / LangChain, feature-gated, returning `serde_json::Value`) plus a Python `as_langchain_tools()` helper (returning `list[BaseTool]`, extras-gated). Also relocate the name-sanitization logic out of `atd-mcp-bridge` into `atd-client` so adapters + bridge share one source of truth. No distribution work — nothing gets published to any registry in this SP.
**Builds on:** v0.1.0 (`sp7-mcp-bridge-validated` + SP-9 release prep) — 250 workspace tests, Rust client without adapters, Python client with OpenAI/Anthropic adapters only.

---

## 1. Motivation

SP-6 + SP-7 closed the protocol-level independence story: atd-client talks to atd-ref-server with zero ANOS dependency, and the MCP bridge proxies that wire to any MCP-speaking agent. That's enough for "wire is neutral" claim. It is not enough for "LLM agents can actually use ATD without writing boilerplate."

Every LLM vendor (OpenAI, Anthropic, LangChain) wants tools in a different shape — name + description + JSON-Schema parameters, wrapped differently per provider. A Rust or Python agent using `atd-client` today has to write that boilerplate itself. Each agent re-implements the same mapping, usually wrong (tool-name sanitization, missing `type: "function"` wrappers, mis-spelled keys).

Shipping adapters moves the mapping into one tested library. One line gets any agent a correctly-shaped tool list. That's the final thing blocking "add `cargo add atd-client` and you can hand ATD tools directly to an LLM."

A secondary goal is collapsing a code-duplication risk: `sanitize_tool_name` already lives in `atd-mcp-bridge/src/sanitize.rs` (and was patched in SP-7 to add the `ref:` namespace). Adapters need the same function. Putting it in one place (`atd-client/src/sanitize.rs`) prevents drift when someone patches one copy and forgets the other.

## 2. Scope

### 2.1 In scope

1. **Sanitize migration.** Move `sanitize_tool_name` + `desanitize_tool_name` from `crates/atd-mcp-bridge/src/sanitize.rs` to `crates/atd-client/src/sanitize.rs`. Update the bridge to import from `atd_client::sanitize`. Bridge's 5 e2e tests must keep passing.
2. **Rust adapters** — three new files under `crates/atd-client/src/adapters/`:
   - `openai.rs` — `as_openai_tools(&[ToolSummary]) -> Vec<serde_json::Value>` producing `[{"type":"function","function":{…}}, …]`
   - `anthropic.rs` — `as_anthropic_tools(&[ToolSummary]) -> Vec<serde_json::Value>` producing `[{"name":"…","description":"…","input_schema":{…}}, …]`
   - `langchain.rs` — `as_langchain_tools(&[ToolSummary]) -> Vec<serde_json::Value>` producing a shape compatible with langchain-rust's `StructuredTool` (or OpenAI-shape fallback if langchain-rust's format can't be verified — see §7 Risks).
   - `resolve_sanitized_id(&str, &[ToolSummary]) -> Option<&str>` helper for reverse mapping after LLM returns a sanitized name.
3. **Feature flags** on `atd-client`:
   ```toml
   default = []
   adapters = ["openai", "anthropic", "langchain"]
   openai = []
   anthropic = []
   langchain = []
   ```
   Each adapter `mod` is `#[cfg(feature = "<name>")]`. Default build excludes all adapters — users opt-in.
4. **Python `as_langchain_tools`** — extend `python/src/atd_client/adapters.py`. Returns `list[BaseTool]` with a factory that wraps each ATD tool as a LangChain `StructuredTool`. Requires `client` argument to wire calls through; if passed `None`, tools exist but calling them raises.
5. **Python extras** — `pyproject.toml` adds `[project.optional-dependencies] langchain = ["langchain-core>=0.3"]`. The langchain-core import in `adapters.py` is lazy: the module imports and `as_openai_tools` / `as_anthropic_tools` still work without `langchain-core` installed. Only `as_langchain_tools` triggers the import, with a helpful error message if extras aren't installed.
6. **Unit tests:**
   - Rust: ~3 per adapter × 3 adapters = ~9 tests. Plus sanitize's existing tests (migrated as-is).
   - Python: ~3 tests for `as_langchain_tools` (shape, missing-extras error, `_arun` invokes `client.call`).
7. **Two examples:**
   - `examples/hello_langchain.rs` — build with `--features langchain`, prints a `Vec<serde_json::Value>` for 3 well-known tools. No LangChain runtime needed at compile time.
   - `python/examples/hello_langchain.py` — uses `as_langchain_tools()`, prints `type(tools[0])` and calls one of them through LangChain's `.invoke()` against a live ref-server (auto-spawn per SP-6 pattern).
8. **Tag** `sp10-adapters` at the final commit.

### 2.2 Explicitly out of scope

- **Distribution**: no `cargo publish`, no `pip publish`, no version bump to 0.2.
- **TypeScript SDK**: deferred until a concrete TS adopter surfaces.
- **`session()` / `cancel()`**: deferred until a use case with real server-side state requirements.
- **Stdio transport on the Rust client**: bridge already covers the stdio use case end-to-end.
- **`atd allow` CLI subcommand**: capability system is Phase 2 per design.md §3.6.
- **Full LangChain e2e**: the Python example calls `.invoke()` but doesn't run a full agent loop (LLM not in CI); unit tests cover shape.
- **langchain-rust as a dep on the Rust adapter**: we emit JSON; if langchain-rust's format is unknowable without actually importing it, the Rust `as_langchain_tools` falls back to OpenAI-shape (documented in the function's docstring).

### 2.3 Prerequisites

- `sp7-mcp-bridge-validated` tag (also at v0.1.0). 250 workspace tests green.
- No new system dependencies.
- `langchain-core` is not required to build/test the core crate — only Python `as_langchain_tools`'s specific tests need it installed.

## 3. Public API

### 3.1 Rust

```rust
// crates/atd-client/src/sanitize.rs  (moved from bridge)
/// Map an ATD tool id to an MCP/LLM-safe identifier.
/// `ref:fs.read` -> `ref_fs_read`; `xiaomi:light.toggle` -> `xiaomi_light_toggle`.
pub fn sanitize_tool_name(tool_id: &str) -> String;

/// Reverse: given a sanitized name, map back to the original tool id.
/// Requires a lookup over known tools because sanitization is lossy
/// (multiple ids can collide to the same sanitized form).
pub fn desanitize_tool_name(sanitized: &str, known: &[&str]) -> Option<String>;
```

```rust
// crates/atd-client/src/adapters/openai.rs  (feature = "openai")
pub fn as_openai_tools(summaries: &[ToolSummary]) -> Vec<serde_json::Value>;

// crates/atd-client/src/adapters/anthropic.rs  (feature = "anthropic")
pub fn as_anthropic_tools(summaries: &[ToolSummary]) -> Vec<serde_json::Value>;

// crates/atd-client/src/adapters/langchain.rs  (feature = "langchain")
pub fn as_langchain_tools(summaries: &[ToolSummary]) -> Vec<serde_json::Value>;

// crates/atd-client/src/adapters/mod.rs  (any feature)
pub fn resolve_sanitized_id<'a>(
    sanitized: &str,
    known: &'a [ToolSummary],
) -> Option<&'a str>;
```

Adapters use the tool's `input_schema` field from `ToolSummary` (already part of SP-1 design). If a summary lacks input_schema (protocol edge case: summary returned without schema), fall back to an empty object `{"type":"object","properties":{}}`.

### 3.2 Python

```python
# python/src/atd_client/adapters.py

def as_openai_tools(summaries: list[ToolSummary]) -> list[dict]: ...  # existing

def as_anthropic_tools(summaries: list[ToolSummary]) -> list[dict]: ...  # existing

def as_langchain_tools(
    summaries: list[ToolSummary],
    client: AtdClient | None = None,
) -> list:  # list[langchain_core.tools.BaseTool], typed at runtime
    """Convert ATD tools to LangChain BaseTool instances.

    If `client` is provided, each returned tool's `_arun()` invokes
    `client.call()` with the sanitized-name mapping applied. If `None`,
    tools list but calling them raises `RuntimeError("client not bound")`.

    Lazy-imports langchain-core. Raises ImportError with pip-install
    hint if the `langchain` extra is not installed.
    """
    ...
```

### 3.3 Feature-gating semantics

Rust's `atd-client` default feature set stays empty (no adapters compiled). Users adopt adapters explicitly:

```toml
# In a downstream crate's Cargo.toml:
atd-client = { version = "0.1", features = ["adapters"] }    # all three
# or
atd-client = { version = "0.1", features = ["openai"] }       # just OpenAI
```

Python's `pip install atd-client` includes the module file with `as_langchain_tools` defined but the lazy import path not exercised. `pip install atd-client[langchain]` makes `as_langchain_tools()` actually work.

## 4. Sanitize migration detail

### 4.1 Current state (bridge)

```rust
// crates/atd-mcp-bridge/src/sanitize.rs
pub fn sanitize_tool_name(tool_id: &str) -> String { ... }
pub fn desanitize_tool_name(sanitized: &str) -> String { ... }  // note: takes &str, not list
```

`desanitize_tool_name` in bridge currently hardcodes known namespace prefixes (`ref`, `anos`, `host`, `mock`) — see SP-7 Task 2. This is fragile — any new server namespace requires a bridge-side patch.

### 4.2 New state (atd-client)

```rust
// crates/atd-client/src/sanitize.rs
pub fn sanitize_tool_name(tool_id: &str) -> String { ... }

pub fn desanitize_tool_name(
    sanitized: &str,
    known: &[&str],  // list of ORIGINAL tool ids to search
) -> Option<String> { ... }
```

Signature change: desanitize now takes a lookup set of known ids and returns `Option<String>`. Implementation strategy: iterate `known`, sanitize each entry, return the matching original on hit. This removes the namespace-prefix hardcoding; any tool id registered in the registry is reachable, no source patch required for new servers.

### 4.3 Bridge migration

Bridge's `lib.rs` (or wherever it does tool-call routing) currently uses:
```rust
use crate::sanitize::desanitize_tool_name;
let original = desanitize_tool_name(&mcp_name);
```

After migration:
```rust
use atd_client::sanitize::desanitize_tool_name;
let known: Vec<&str> = cached_tools.iter().map(|t| t.id.as_str()).collect();
let original = desanitize_tool_name(&mcp_name, &known)
    .ok_or_else(|| format!("unknown tool: {mcp_name}"))?;
```

Bridge keeps a `cached_tools: Vec<ToolSummary>` (it already does, for the `tools/list` response). The desanitize call simply borrows id refs from that cache.

### 4.4 Bridge tests

Bridge has its own sanitize unit tests. They migrate to `atd-client/src/sanitize.rs` along with the code. Bridge's 5 integration e2e tests (from SP-7) do NOT change — they test behavior through stdio + wire, not the sanitize API directly. They must keep passing after migration.

## 5. LangChain Python adapter detail

LangChain's `StructuredTool` is the path-of-least-resistance. Given:

```python
from langchain_core.tools import StructuredTool
from pydantic import create_model

def _make_tool(summary: ToolSummary, client: AtdClient | None) -> StructuredTool:
    sanitized_name = sanitize(summary.id)  # reused logic
    args_model = _schema_to_pydantic_model(summary.input_schema)

    async def _arun(**kwargs):
        if client is None:
            raise RuntimeError(
                f"ATD tool {summary.id} has no client bound; "
                f"pass client= to as_langchain_tools()."
            )
        result = await client.call(summary.id, kwargs)
        if isinstance(result, ToolFailure):
            raise RuntimeError(f"[{result.code}] {result.message}")
        return result.data

    return StructuredTool.from_function(
        coroutine=_arun,
        name=sanitized_name,
        description=summary.description,
        args_schema=args_model,
    )
```

`_schema_to_pydantic_model` converts the ATD tool's `input_schema` (JSON Schema) into a Pydantic v2 model. Minimum viable subset: `type: object` with `properties` where each property is `type: string / integer / boolean / number / array / object`. Things outside this subset (e.g., `oneOf`, nested complex types) map to a permissive `dict[str, Any]` — LangChain accepts it; runtime validation happens on the ATD side anyway.

### 5.1 Python sanitize availability

Python side currently has no sanitize function. LangChain adapter needs one.

- **Option A:** Port a minimal Python `_sanitize()` into `adapters.py` (20 lines of regex). Risk: drift between Rust and Python implementations.
- **Option B:** Have a single test in Python that round-trips through a subprocess call to `atd-client`'s sanitize binary. Too complex for the value.
- **Option C:** Just port it. Add a shared test fixture — same list of 20 tool ids, same expected outputs, both Python and Rust test against them. Drift catches in CI.

**Pick C.** Small function, small maintenance burden, high determinism.

## 7. Risks and non-risks

### 7.1 Risks

**R1 — langchain-rust shape is unknown or unstable.** `langchain-rust` is a pre-1.0 crate with small community. Its `StructuredTool` serialization format may not be ergonomic to emit as JSON without actually depending on the crate.

*Mitigation:* the Rust `as_langchain_tools` docstring will declare "emits a shape compatible with langchain-rust ≥0.1.x; if you are on a different LangChain Rust implementation, use `as_openai_tools` which is widely compatible." If during implementation langchain-rust's shape can't be determined without importing the crate, we fall back to emitting OpenAI-shape and document it. Zero Rust dep on langchain-rust either way.

**R2 — Rust adapter feature flag complexity.** Three-level features (`adapters` meta + 3 individual) can confuse `cargo tree` readers.

*Mitigation:* `default = []` keeps the naive build clean. `--features adapters` is the documented "give me everything" path. Individual features are opt-in for users who want minimal deps.

**R3 — Python pydantic v2 vs v1.** langchain-core 0.3+ requires pydantic v2; earlier pydantic in the env causes obscure errors.

*Mitigation:* pin `langchain-core>=0.3` in the extras; add a version check at lazy-import time with a clear error message if langchain-core<0.3 is found.

**R4 — desanitize collision.** Two tool ids sanitizing to the same name (`a:b` and `a.b` both → `a_b`) is possible. The new list-based desanitize returns the first match, deterministically — but callers may be surprised.

*Mitigation:* sanitize function adds a disambiguator for collisions (e.g., include a short hash suffix when the sanitized form collides with an already-used one within the given list). Detection is cheap since the adapter already iterates all summaries. Implementation lives in `sanitize.rs` + tested in `sanitize::tests::collision_gets_disambiguator`.

### 7.2 Non-risks

- **Protocol drift**: adapters are pure `ToolSummary → JSON` transformations; they don't touch the wire.
- **Bridge backward compat**: the sanitize migration moves code to a new module but the bridge's external behavior (MCP protocol) is unchanged. 5 e2e tests prove this.
- **Feature-gated build**: `cargo check --workspace` without adapter features must pass cleanly — no dangling dead code, no unresolved imports.

## 8. Exit criteria

1. `cargo test --workspace --all-targets` — ≥259 tests, 0 failures
2. `cargo build --workspace` — clean, no warnings
3. `cargo build -p atd-client --features adapters` — compiles with all adapters on
4. `cargo build -p atd-client` — compiles with adapters off (default)
5. `cargo build --example hello_langchain -p atd-examples --features langchain` — compiles
6. `uv run python python/examples/hello_langchain.py` — runs successfully against auto-spawned ref-server (or skips cleanly with a TODO note if langchain extras aren't installed in the test env)
7. `cargo test -p atd-mcp-bridge --test integration_e2e` — still passes (5/5, same as before SP-7 baseline)
8. Python `pytest python/tests/test_adapters.py` — passes (3 new tests + existing)
9. Tag `sp10-adapters` at the final commit
10. No registry publish, no version bump; 0.1.0 remains 0.1.0

## 9. What SP-10 does NOT unlock

- External Rust adopter downloads `cargo add atd-client --features adapters` — not yet, because atd-client is still unpublished. User does manual publish after this SP if they want.
- LangChain agent uses ATD tools in a real LLM loop — the Python example invokes one tool, but doesn't run a full LangGraph/AgentExecutor. A downstream user does that in their own codebase.
- TypeScript world — still untouched.

Those are downstream of SP-10's artifact, not in-scope for it.
