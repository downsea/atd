# SP-8.1 — Capability-denied gated tool for cross-impl conformance

**Date:** 2026-04-24
**Status:** Approved — ready for implementation plan
**Parent:** SP-8 (conformance suite) — closes the I-1 audit finding.
**Anchor:** SP-8 final review §I-1; SP-8 spec §7.2 (`conformance.denied` capability convention).

## 1. Context

SP-8 shipped the cross-implementation conformance suite (`atd-conformance`) but had to remove one planned fixture during implementation: `capability_denied_returns_code_1001`. Every built-in tool in the reference server (`atd-tools-echo`, `atd-tools-fs::*`, `atd-tools-shell::*`, `atd-tools-web::fetch`, `ref:external.uname`) declares `required_capabilities: vec![]`, so no call path naturally triggers `ERR_CAPABILITY_DENIED` (code 1001). The in-tree test `dispatch_capability_denied_path.rs` covers the path with a locally-declared `GatedTool`, but that path is unreachable from a black-box conformance driver.

Net effect: a third-party ATD server today can pass the conformance suite while completely failing to honor the 1001 wire contract from SP-12. That's a real spec-coverage gap.

This SP closes it by adding a conformance-suite-specific demo tool to the reference server, gated behind a runtime CLI flag so production usage is unchanged.

## 2. Decisions locked in during brainstorming

| # | Question | Answer |
|---|---|---|
| Q1 | Activation mechanism? | A — Runtime CLI flag `--enable-conformance-tool`. Zero production pollution when omitted; opt-in and explicit. |
| Q2a | Tool id? | `ref:conformance.denied_op`. `ref:` namespace marks it as ref-server-native; `conformance.` subdomain signals its purpose. |
| Q2b | Required capability? | `["conformance.denied"]` — matches the opaque-string convention defined in SP-8 spec §7.2; test harness never grants it. |
| Q3 | Fixture scope? | A — Restore only `capability_denied_returns_code_1001.json`. "Granted" path is already exercised by other fixtures using real ref-server capabilities (e.g., `read`). |

## 4. `ConformanceDeniedTool` implementation

File: `crates/atd-ref-server-bin/src/conformance.rs`

```rust
//! Conformance-suite-specific tools — registered ONLY when
//! `--enable-conformance-tool` is passed. These tools exist solely so the
//! `atd-conformance` suite can validate protocol paths (like
//! `ERR_CAPABILITY_DENIED` / code 1001) that no production built-in tool
//! naturally exercises.

use atd_protocol::{
    BindingProtocol, SafetyLevel, ToolBinding, ToolCapability, ToolDefinition,
    ToolResources, ToolSafety, ToolTrust, ToolVisibility, TrustLevel,
};
use atd_runtime::context::CallContext;
use atd_runtime::error::ToolCallError;
use atd_runtime::registry::{CallFuture, Tool};

/// A trivial tool that requires the `conformance.denied` capability.
/// The test harness never grants this capability, so every call is
/// short-circuited by the dispatch layer with `ERR_CAPABILITY_DENIED`
/// before `call` ever runs. If `call` *does* run, that's a bug in the
/// capability gate — we return an `InternalError` sentinel so the
/// violation is loud.
pub struct ConformanceDeniedTool {
    def: ToolDefinition,
}

impl ConformanceDeniedTool {
    pub fn new() -> Self {
        Self {
            def: ToolDefinition {
                id: "ref:conformance.denied_op".into(),
                name: "conformance denied op".into(),
                description:
                    "Test tool: requires 'conformance.denied' capability. \
                     Exists only to let atd-conformance validate the \
                     ERR_CAPABILITY_DENIED (code 1001) wire path. Enabled \
                     via --enable-conformance-tool.".into(),
                version: "0.0.0".into(),
                capability: ToolCapability {
                    domain: "conformance".into(),
                    actions: vec!["denied_op".into()],
                    tags: vec!["test".into()],
                    intent_examples: vec![],
                },
                input_schema: serde_json::json!({ "type": "object" }),
                output_schema: serde_json::json!({ "type": "object" }),
                bindings: vec![ToolBinding {
                    protocol: BindingProtocol::Cli,
                    config: serde_json::json!({}),
                }],
                safety: ToolSafety {
                    level: SafetyLevel::Read,
                    dry_run: false,
                    side_effects: vec![],
                    data_sensitivity: None,
                },
                resources: ToolResources {
                    timeout_ms: 1000,
                    max_concurrent: 1,
                    rate_limit_per_min: None,
                    estimated_tokens: None,
                },
                trust: ToolTrust {
                    publisher: "atd-ref-server".into(),
                    trust_level: TrustLevel::L0Unverified,
                    signature: None,
                },
                visibility: ToolVisibility::Read,
                required_capabilities: vec!["conformance.denied".into()],
                tier: None,
            },
        }
    }
}

impl Default for ConformanceDeniedTool {
    fn default() -> Self {
        Self::new()
    }
}

impl Tool for ConformanceDeniedTool {
    fn definition(&self) -> &ToolDefinition {
        &self.def
    }

    fn call<'a>(&'a self, _args: serde_json::Value, _ctx: &'a CallContext) -> CallFuture<'a> {
        Box::pin(async {
            Err(ToolCallError::InternalError(
                "ref:conformance.denied_op was reached by dispatch — \
                 capability gate should have rejected with code 1001".into(),
            ))
        })
    }
}
```

### Why each metadata choice matters

- `required_capabilities: ["conformance.denied"]` — matches the SP-8 §7.2 opaque-string convention.
- `trust_level: L0Unverified` — marks the tool as non-production for any future trust-audit middleware.
- `publisher: "atd-ref-server"` — consistent with other ref-server-native tools; a `publisher == "atd-ref-server"` check remains a reliable filter.
- `tier: None` — no tier budget applies; dispatch never reaches the tier stage because capability denial short-circuits earlier.
- `bindings: [Cli]` — required field; dispatch uses the capability gate before binding resolution, so this is inert.
- `call` body as a loud sentinel — defense-in-depth; a correct dispatch layer never invokes it, but a regression in the capability gate surfaces as a specific `InternalError` rather than silently returning a sentinel success.

## 5. `builtin_registry` signature change

Current:
```rust
pub fn builtin_registry() -> Registry {
    let mut reg = Registry::new();
    // ... register 10 production tools ...
    reg
}
```

New:
```rust
pub fn builtin_registry(enable_conformance_tool: bool) -> Registry {
    let mut reg = Registry::new();
    // ... register 10 production tools (unchanged) ...

    if enable_conformance_tool {
        use crate::conformance::ConformanceDeniedTool;
        reg.register(Arc::new(ConformanceDeniedTool::new()));
    }

    reg
}
```

Impact:
- `main.rs` is the only production call site — update to pass the new flag value.
- Existing unit test `builtin_registry_contains_all_tools` updates its call to `builtin_registry(false)` (verifying the default / no-flag path still yields 10 tools on unix, 9 elsewhere).
- Add a second unit test `builtin_registry_with_conformance_tool_adds_one`:
  - `builtin_registry(true).count() == builtin_registry(false).count() + 1`
  - `builtin_registry(true).get("ref:conformance.denied_op").is_some()`
  - `builtin_registry(false).get("ref:conformance.denied_op").is_none()`

## 6. CLI flag in `main.rs`

```rust
/// Register a test-only conformance tool (ref:conformance.denied_op) that

```

## 7. Conformance fixture (C2)

New file `crates/atd-conformance/fixtures/behavior/capability_denied_returns_code_1001.json`:

```json
{
  "category": "behavior",
  "name": "capability_denied_returns_code_1001",
  "description": "Calling a tool whose required_capabilities aren't granted returns Response::Error { code: 1001, retryable: false }. Requires the target server to expose a capability-gated tool — the atd-mvp reference server does this via `ref:conformance.denied_op` (registered when `--enable-conformance-tool` is passed). Third-party servers that want to validate this case must expose a tool with id `ref:conformance.denied_op` requiring capability `conformance.denied` (and NOT grant that cap by default).",
  "setup": null,
  "send": {
    "type": "run_tool",
    "tool_id": "ref:conformance.denied_op",
    "args": {},
    "dry_run": false
  },
  "expect_response_matches": {
    "type": "error",
    "code": 1001,
    "retryable": false
  }
}
```

### Why `setup: null`

A freshly-opened connection has capability set `{}` (no Hello performed). The tool requires `{"conformance.denied"}`. Subset check `{"conformance.denied"} ⊆ {}` fails → dispatch emits 1001 before invoking the tool. No Hello handshake needed.

## 8. Self-conformance test update (C2)

Current `spawn_server` in `crates/atd-conformance/tests/atd_mvp_self_conformance.rs`:

```rust
Command::new(bin)
    .arg("--sock").arg(sock)
    .arg("--grant-capability").arg("read")
    .arg("--grant-capability").arg("write")
    .arg("--grant-capability").arg("exec")
    .stdout(Stdio::null())
    .stderr(Stdio::null())
    .spawn()
```

Becomes (one added `.arg`):

```rust
Command::new(bin)
    .arg("--sock").arg(sock)
    .arg("--grant-capability").arg("read")
    .arg("--grant-capability").arg("write")
    .arg("--grant-capability").arg("exec")
    .arg("--enable-conformance-tool")
    .stdout(Stdio::null())
    .stderr(Stdio::null())
    .spawn()
```

**Crucial:** do NOT add `--grant-capability conformance.denied`. The absence of that grant is what makes `ref:conformance.denied_op` calls fail with 1001.

The existing `assert!(report.total >= 28 && report.total <= 35, ...)` assertion needs no change — restoring the fixture moves total from 31 to 32, still in range.

## 9. Non-goals

| Not doing | Why | When it opens |
|---|---|---|
| Multiple capability-gated demo tools | YAGNI — one tool covers the 1001 path | Only if future spec mandates multiple distinct capability-error flavors |
| "Capability granted" fixture targeting the new tool | Granted-path coverage already exists via real tools (e.g., `read` + `ref:fs.read`) | — |
| Machine-readable documentation of `ref:conformance.*` family | Single tool; inline fixture description is enough | If the family grows past 2-3 tools |
| Environment variable activation (`ATD_ENABLE_CONFORMANCE_TOOL=1`) | CLI flag is more discoverable and explicit | Only if we find a CI harness where flags can't be passed |
| Cargo-feature gating (build-time) | Third-party Rust implementers don't rebuild ref-server | — |
| Separate `atd-ref-server-conformance` binary | 2x maintenance cost for marginal clarity gain | — |
| Removing `dispatch_capability_denied_path.rs` now that conformance covers 1001 | Different level: that's an in-process test of the capability gate internals; conformance is black-box | Never — keep both |

## 10. Success criteria

SP is complete when **all** hold:

1. `./target/release/atd-ref-server --sock /tmp/s.sock` (no new flag) registers exactly the 10 production tools (9 on non-unix). Confirmed via `atd --sock /tmp/s.sock list`.
2. `./target/release/atd-ref-server --sock /tmp/s.sock --enable-conformance-tool` registers 11 tools; the extra one is `ref:conformance.denied_op`.
3. `cargo test -p atd-ref-server-bin --lib builtin` passes both `builtin_registry_contains_all_tools` (10/9 count) and `builtin_registry_with_conformance_tool_adds_one`.
4. `cargo test -p atd-conformance --test atd_mvp_self_conformance` passes; `report.total == 32`, `report.failed == 0`.
5. Full 4-gate green: `cargo fmt --check` + `cargo clippy --workspace --all-features -- -D warnings` + `cargo test --workspace --all-targets` + `cargo build --release --workspace`.
6. Workspace test count 320 + 2 (the new unit test + the restored fixture's addition to self-conformance is counted in the existing test; only `builtin_registry_with_conformance_tool_adds_one` is a net +1 Rust test) = 321. The actual new-test delta is 1; conformance fixture count goes 31 → 32.
7. Zero changes outside `atd-ref-server-bin` and `atd-conformance`.
8. No `.github/workflows/ci.yml` changes.
9. SP tagged `sp-8.1-capability-denied-gated-tool` on completion.

## 11. Rollback

Before starting: `git tag pre-sp-8.1-capability-denied-gated-tool`. Each of C1 and C2 independently reversible. Worst case: `git reset --hard pre-sp-8.1-capability-denied-gated-tool` removes all SP changes.

## 12. Next steps unlocked

- **Third-party ATD implementers** can now self-validate the 1001 contract against their own server — they just need to expose a tool with id `ref:conformance.denied_op` requiring capability `conformance.denied`, and not grant that cap by default. The fixture description is explicit about this.
- **Closes SP-8 review finding I-1.** The originally-specified 32-case count is restored.
- **Sets the pattern** for any future "protocol path that needs a specially-shaped tool to exercise" — runtime flag + single-purpose gated tool + fixture that points at it.
