# Phase 0.5 Validation — Hermes End-to-End

**Date:** 2026-04-21
**Goal (design.md §1.1 Goal A):** Non-ANOS agent calls an ATD tool via atd-client, end to end.
**Scope:** Discovery path only (tools/list). Execution (tools/call) blocked on ANOS-side gap — see docs/issues/2026-04-21-atd-run-tool-stub.md.

## What works

- ✅ `atd-mcp-bridge` connects to ANOS daemon over Unix socket (`~/.anos/anos.sock`)
- ✅ MCP `initialize` handshake echoes protocolVersion 2025-11-25
- ✅ MCP `tools/list` returns all ANOS hot tools (108 locally), sanitized to `anos_fs_read` form
- ✅ `hermes mcp add atd --command <bridge>` registers the server (saved to `~/.hermes/config.yaml`, 108/108 tools enabled)
- ✅ `hermes mcp test atd` exits 0, reports **108 tools** discovered in 361ms
- ✅ `hermes tools list` shows `atd` MCP server under "MCP servers:" with all tools enabled

## What is blocked

- ❌ End-to-end tool execution (`tools/call`) — ANOS's `run_tool` IPC handler returns
  `{"type":"error","message":"direct tool execution via IPC not yet supported — use RunTurn"}`.
  The bridge correctly forwards this as an MCP `isError=true` content block, so Hermes sees
  an honest failure rather than a silent hang. Resolving this requires ANOS-side work
  (tracked in `docs/issues/2026-04-21-atd-run-tool-stub.md`).
